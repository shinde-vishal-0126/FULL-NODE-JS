2. Origin Access Control (OAC) Architecture

OAC is recommended for new S3 origins. It signs origin requests with SigV4 and supports SSE-KMS configurations. OAI is a legacy mechanism with limitations, including lack of SSE-KMS support; avoid describing it simply as SigV2.

6. 25+ Mid-to-Senior S3 & CloudFront Interview Questions

Q01: What is the difference between Origin Access Identity (OAI) and Origin Access Control (OAC)?

Answer: OAI is a legacy S3 origin-access mechanism with limitations, including lack of SSE-KMS support; avoid characterizing it simply as SigV2. OAC is recommended for new S3 origins: it signs requests with SigV4 and permits a bucket policy scoped to the distribution ARN.

Q02: When should you use Signed URLs vs Signed Cookies?

Answer: Signed URLs suit individual files and clients that do not send cookies. Signed Cookies are convenient for HLS or multiple private resources when the player sends cookies on every request; signed URLs can also work if the player can sign or rewrite each resource URL.

Q03: How do you eliminate the "Thundering Herd" problem when video traffic spikes?

Answer: Consider CloudFront Origin Shield to reduce duplicate origin fetches for concurrent misses. Request collapsing depends on cache key and timing; it does not guarantee exactly one origin request for every global miss.

Q04: Why is running `create-invalidation --paths "/*"` dangerous in CI/CD?

Answer: A wildcard invalidation can cause a burst of cache misses and increased origin requests. Pricing and free allowances can change; /* counts as one path. Prefer versioned hashed filenames and check current AWS pricing.

Q05: What is the Claim-Check Pattern in S3 + SQS / CloudFront architectures?

Answer: For payloads exceeding SQS's 256 KB limit, upload the large file to S3, send a lightweight reference pointer (claim check) to SQS, and have consumers retrieve the object from S3 or CloudFront.
